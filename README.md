# wallet-transactions
The wallet-transactions CI/CD pipeline has four sequential quality gates, each pass after which the next stage is executed. This ensures that no code will be packaged unless it passes all of the automated tests.
This is the unit tests for Gate 1 (lint-and-test: Job).
All commits to main and pull requests are automatically tested via pytest. There are 15 test cases for all five API endpoints, including normal, edge cases, and error handling. Enforces a minimum code coverage threshold of 80%, the pipeline will fail and block if coverage is below or if a single test fails. Test results and coverage report (coverage.xml) are uploaded as a pipeline artefact, which cannot be modified, as evidence of quality controls.
404: No security gates found (Job: security-scan).
Once Gate 1 passes, 3 security tools are automatically activated. Bandit does Static Application Security Testing (SAST) on the Python source code and identifies unsafe coding patterns. Check the requirements.txt file for security vulnerabilities in the project's dependencies against the CVE list. Gitleaks checks the entire git commit history for any accidentally committed secrets, credentials, or API keys. This gate is a direct response to MeridianPay Incident 2 – 13 days critical CVE patch delay, which was due to manual processes. With this gate, vulnerabilities are detected within minutes of being introduced.
There is a second gate that is called Integration Tests (Job: integration-test). There's another gate called Integration Tests (Job: integration-test).
The Flask API is launched as a live process, and four different integration scenarios are run at the HTTP level against real endpoints, with end-to-end testing of transaction flows, insufficient funds rejection, and 404 compliance of the contract with unknown wallets. This is a gate to prevent the API contract failures that were experienced in MeridianPay Incident 3.
This step (build-and-package) is located at Gate #4.
Only gets to after all 3 gates pass. Generates a versioned ZIP artefact, and a SHA256SUMS.txt integrity manifest that proves that the deployed code is the same code that passed tests. They both remain as pipeline artifacts for 90 days.
Automated vs Risk-Based: All four gates are fully automated and are processed without any human interaction on every single push, which is a pre-approved Standard Change according to the ITSM change enablement model. When all gates pass, there is no manual approval required. Human review is only called in when a gate fails, which reflects the notion of DevSecOps that automation takes the easy route and escalation takes place on the truly risky route.
